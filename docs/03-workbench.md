# 03 · 六品牌工作台

`workbench/` · 10 个页面 · 纯静态 · 零构建 · 部署时发到星河的 `public/wb/`

## 它要回答的问题

不是「有哪些内容」，而是「**我的品牌和别人比，到底差在哪**」。

这个问题难在两个地方：

1. **口径不统一**：A 品牌 3000 条、B 品牌 800 条，直接比数量没意义。
   A 的 3000 条里可能 1900 条只是搜索词命中了、正文根本没提品牌。
2. **看不到证据**：客户看到的每个数字都要能追到原文，否则第一句质疑就是
   「这数怎么来的」。

工作台的答案：先把口径统一（证据三级 + 同规则判定），再让你看数字，
并且每个数字都能点进原文。

### 为什么是现算不是预生成

早期是构建期生成 `list-*.js` 静态文件。问题：

- 数据更新要重新构建 → 每天更新数据等于每天重新部署
- 静态文件进 git → 客户数据进仓库
- 数字对不上时无法判断是数据旧还是逻辑错

现在按请求现算 + TTL 缓存（`_cached(key, ttl, fn)`）。代价是首次请求约 200ms，
之后命中缓存。换来的是：**数据永远是新的，改口径不用重新部署**。

### 缓存策略

```python
def _cached(key, ttl, fn):
    now = time.time()
    with _LOCK:
        hit = _CACHE.get(key)
        if hit and now - hit[0] < ttl:
            return hit[1]
    val = fn()
    with _LOCK:
        _CACHE[key] = (now, val)
    return val
```

粗粒度、进程内、按 key。没有 Redis，没有失效通知 —— 采集是每天一次，
TTL 到点自然更新就够了。要立刻生效就重启（`cache_clear()` 也留了）。

## 口径怎么算

### 三个基础指标

```python
def tri(rows):
    """[条数, 均赞, 爆文数]"""
    L = [likes_of(r["metrics_json"]) for r in rows]
    n = len(L)
    return [n, round(sum(L)/n) if n else 0, sum(1 for x in L if x >= 1000)]
```

| 指标 | 定义 | 为什么这么定 |
|---|---|---|
| 条数 | 已校验内容数 | 反映真实声量，不含蹭词位 |
| 均赞 | 总赞 / 条数 | 反映单条质量，避免"量大声量小" |
| 爆文数 | 点赞 ≥ 1000 的条数 | 抗衰品类的内容天花板参考 |

**均赞比总赞更有用**。总赞会被条数放大，一个品牌发 3000 条烂内容总赞也好看。

### 分桶

```python
def bucket_of(l):
    if l >= 10000: return "≥1w"
    if l >= 1000:  return "1k-1w"
    if l >= 100:   return "100-1k"
    return "<100"
```

按互动量把内容分四档，看的是**分布形状**而不是平均数。
一个品牌 90% 内容在 `<100`、另一个 50% 在 `1k-1w`，均赞可能差不多，
但后者明显更健康。

### 官方号标记

```python
def is_off(r):
    return "official" in (r.get("tags") or "")
```

统计时可以把官方号内容剔除，看到的是**纯自来水**声量。
官方号发 100 条不算本事。

## 前端约束

工作台页面是**零构建**的：没有 webpack、没有 npm、没有打包步骤。
每个 `.html` 直接引 `<script>`，改完刷新就是新的。

代价是不能用 JSX / TS / CSS 预处理器。对这个规模（
10 个页面共 2714 行）不值得为此引入构建链——服务器在内网，
多一个构建步骤就多一种「本地能跑服务器跑不起来」的可能。

三条前端规矩：

1. **不许内联大数据**。所有数据 fetch `/api/wb/*`，页面文件本身不含业务数据。
2. **不许硬编码 IP 或端口**。全部相对路径 `/api/wb/...`，换域名不用改前端。
3. **数字必须可点**。总盘上的每个数字点进去能看到构成它的内容列表，
   否则就是黑盒。
